# DAQ FAE 与相机 FAE 回答质量对比分析设计

**日期**：2026-10-20

**状态**：分析设计；尚未形成当前生产质量结论

**目标**：定位数采 FAE 在移植后为何出现回答过短、已有资料却答不出，以及其他可观察的质量退化。先建立可复核的因果证据，再决定修改代码、提示词或知识的范围。

## 1. 已知事实与待验证判断

- 两仓当前提交的共享 `src` Git 树相同（`e69021117158cbdc7e6d75220c5247fe631bbe58`）；DAQ 的入口装配、请求 schema、目标账本、领域工具、证据策略和提示词位于 `daq_fae/`、`prompts/`，由 DAQ 独立维护。共享树一致不证明两套端到端行为一致。
- [2026-10-20 DAQ 发布记录](../../reviews/2026-10-20-daq-scenario-production-release.md)绑定生产代码 `7d7232902cdd6cdea2baf4d61ccc0960ef1ab428`、运行时 `daq-ba50906bd98b`、27 条主知识、24 条 SDK 用法和 17 条日志。最终代码身份下 55 道核心题未整套重跑，多轮完成 9/13 组；聚焦 Dev 题不能外推为整体质量通过。生产未运行模型评测。
- [2026-10-18 独立复审](../../reviews/2026-10-18-daq-current-release-codex-review.md)在旧发布身份发现过“已发布 HUB 规格漏答”“单机流程被组合目标遮蔽”“未核实硬条件却肯定推荐”等真实错误；这些是历史哨兵，不能直接称为 2026-10-20 生产仍存在的同一错误。
- 2026-10-20 随发布保存的少量 Dev 答案有数百字，部分超过 800 字。因此“生产回答很简短”需要具体用户 turn、后端终稿和前端展示相互对照；不能单凭提示词长度或这批聚焦答案判定原因。
- [原件覆盖审计](../../reviews/2026-10-16-daq-full-material-coverage.md)显示“已归档”和“可回答的已审发布”差距很大。确实缺知识与有知识但未使用必须分开计数。

以上只读事实给出调查入口，不预先断定当前短答由模型、知识量、证据门或 UI 单独造成。

## 2. 方案选择

| 方案 | 能回答什么 | 主要不足 |
| --- | --- | --- |
| 仅比较 Git、配置与提示词 | 快速找出移植差异和明显契约错位 | 无法证明这些差异造成用户看到的短答 |
| 只做答案盲评 | 可量化用户感受到的完整性、专业性和可操作性 | 很难知道内容在哪一层丢失，容易催生提示词补丁 |
| **以真实失败为锚的逐层追踪，辅以同类任务盲评** | 同时确认质量差距和最早失效层，区分无知识、漏检、误拦、漏写与展示问题 | 需要冻结版本、取得可用 trace，并对不同产品域建立公平的对应题型 |

采用第三种。前两种分别作为它的静态检查和答案评价步骤。

## 3. 比较口径与样本

### 3.1 两种比较，分别回答两个问题

1. **DAQ 自身的证据兑现**：对用户真实数采问题，依据当时角色可见的 DAQ 发布快照，列出“应答单元”（明确结论、适用条件、依据、操作检查点、缺口和下一步）。检查 Agent 是否把本轮可取得的证据交付给用户。这是定位“答不出来”的主口径。
2. **跨 Agent 的能力对照**：用同类型、难度相近且各自领域都有已审证据的问题，比较单事实、条件规格、混合目标、选型、SDK、排障、多轮等处理能力。相机 FAE 不回答 DAQ 产品事实，DAQ 也不借用相机事实。比较的是任务完成方式和专业度，不是两个知识库覆盖总量或绝对答案字数。

如果两侧模型、网关、提示、可用知识或角色不同，逐项记录；不能把这些变量统称为“移植效果”。同一题型至少保留一个正向有据例和一个缺证边界例。实际用户差评优先于人工构造题；没有对应来源的样本保留为“知识缺口”，不强行配成相机对照题。

### 3.2 样本入口与冻结身份

- 第一批以用户报告的短答、空答、错误弃答和“答了但不解决问题”为锚。保存脱敏的问题、必要会话历史、附件类型、用户实际看到的文字、时间与 trace ID；不把客户原始附件写进 Git。
- 复用已有 DAQ Dev 结果与旧失败哨兵，按其原代码、知识、提示和模型身份标记为**历史证据**。不同身份的答案不合并成一个通过率。
- 核实最新生产身份时仅做只读 health、发布清单和已有日志核对。新模型回放只在隔离 Dev 进行；不向生产 `/chat` 发送评测题。2026-10-20 发布的聚焦结果与未完成的全量范围原样保留。
- 每个回放保存 DAQ/相机代码 SHA、提示词 SHA、知识发布 ID、模型回显、网关协议、角色、题集 SHA、结果与 trace SHA。用户问题、结果和附件若含内部信息，放在 Git 忽略的受限目录；跟踪文档只放脱敏摘要、哈希和定位信息。

首批目标是取得覆盖两类用户症状的约 20–30 个独立 turn；若真实样本不足，先分析全部可得样本并标明覆盖不足，不用合成题冒充生产反馈。

## 4. 从用户输入到可见答案的逐层追踪

```text
用户原问/历史/附件
  → 入口、身份和语言
  → 有效问题、上下文与边界
  → schema 子目标、实体与条件
  → 计划能力和可调用工具
  → 工具查询、返回记录与来源范围
  → 需求账本和证据覆盖
  → submit_answer 字段与 outcome
  → 服务端渲染、SSE、持久化与前端展示
```

每个失败样本记录相邻层的**输入、输出与丢失项**。先确定最早偏离用户目标或受审来源的层，再追问为什么。若某层 trace 缺失，将“不可定位的观测缺口”单列，不从最终答案反推它一定发生了什么。

| 层 | 核对问题 | 典型归因 |
| --- | --- | --- |
| 入口/展示 | 后端 `done.answer`、SSE 拼接、历史与浏览器可见答案是否一致？ | 真截短、会话串位、语言或 UI 展示差异 |
| 上下文/schema | 用户问了几个目标？设备、变体、测量条件、软硬条件和追问指代是否保留？ | 错拆/漏拆目标、假定条件、切题污染 |
| 工具/知识 | 应用可见发布里是否有同范围记录？工具是否调用、命中、被过滤或返回错误？ | 真知识缺口、检索缺口、查询标签不匹配、权限范围 |
| 覆盖/终态 | 已命中来源是否计入对应目标？部分有据时为何提交弃答？ | 证据映射错误、过严/过松的门、错误 outcome |
| 合成/渲染 | 模型 `submit_answer` 各字段与最终正文相比，哪些有据事实、操作步骤或建议被省略？ | 已知部分漏写、提示词压缩、字段规则/渲染顺序影响 |

对“答不出来”固定区分：**当前版本确无权威资料、资料存在但未发布、已发布但未检到、已检到但目标未获覆盖、覆盖已满足但模型漏答、运行/Provider 失败、前端未完整展示**。这些类别对应不同的改进责任，不能都归为模型能力差。

## 5. “很简短”的评价方法

原始字数和 token 数只作描述统计。单项规格题简短且答全是正常结果；多目标排障题只给一句“资料不足”则可能是严重漏答。

每题先由独立复审者按用户意图与当时权威来源列出应答单元，并标记 `required / useful / unsupported`。记录以下指标：

- **已知事实兑现率**：已通过本轮工具取到且与问题相关的 `required` 单元，有多少进入用户可见答案；同时记录来源、实体、变体和条件是否保持一致。
- **子目标完成率**：用户明确提出的目标中，已答、部分答、合理弃答和漏答各有多少。混合问题不能被一个未知目标抹掉所有已知部分。
- **弃答准确性**：`safe_abstained` 是否确有关键缺口；是否仍交付可安全回答的局部事实和最小下一步；是否把工具故障误说成资料缺失。
- **工程可用性**：对排障/SDK/流程题，是否给出来源支持的可执行步骤、核对点与适用边界；禁止用篇幅增加代替有效内容。
- **表达质量**：结论是否先说清、有没有重复缺证或内部流程话术、长度是否与问题复杂度相称。

评分沿用相机仓[四轴口径](../../../../AI-FAE-Agent/docs/architecture/评测四轴与运行时去补丁设计_20260714.md)：语义/事实、运行硬门、协议一致性、展示质量分开。回答模型不评自己的答案；自动断言只做预检，最终逐题由 Codex 或人工 FAE 阅读完整问答与来源。盲评时隐去 Agent 名称，另保存原始身份供因果追踪。

## 6. 待检验假设与最小验证

| 假设 | 可证伪的观察 | 最小验证 |
| --- | --- | --- |
| DAQ 已发布知识不足 | 相同实体/条件在角色可见发布里没有记录 | 核对发布清单、候选与原件；列为知识治理缺口，不动提示词 |
| schema 或工具映射让已审事实漏检 | 来源存在，但目标/工具参数或匹配 ID 在进入模型前丢失 | 用原问题和冻结发布做无模型工具重放，再看一次 Dev trace |
| 证据门把局部答案压成短弃答 | 工具已返回相关事实，但账本保持未知/缺失，`submit_answer` 丢掉已知部分 | 对照需求状态、策略反馈、提交字段及渲染正文 |
| 提示词的简洁规则或字段约束抑制展开 | 目标与证据完整，模型仍省略必需单元；相近题反复出现 | 先做字段级诊断；有必要时只在 Dev 对单一变量做提示消融，保留来源与安全约束 |
| 展示层造成“用户看到更短” | 后端终稿完整而 SSE、历史或浏览器显示缺段 | 对同一 trace 比对终稿、流、持久化和 UI |
| 模型/网关行为差异 | 同一冻结输入与知识下，配置或 Provider 实际回显不同 | 先核实版本与传输错误；仅在前述层排除后做隔离 Dev 对照 |

先验证单一假设，再决定最小修复。不得用最终答案关键词扫描、按原题硬编码或把候选资料直接升格为权威答案来提高表面通过率。

## 7. 分析执行顺序与交付

1. **建立样本与身份表**：锁定用户真实 turn、最新 DAQ 发布身份及各历史结果身份；按“短答/答不出/错答/多轮”去重，标明缺失的生产 trace。
2. **先判展示是否一致**：对短答优先核对用户看到的文本与后端 `done.answer`，避免把 UI 问题误修到模型或知识。
3. **逐题回溯**：为每题画出应答单元、可用证据、实际工具返回、需求状态、提交字段和最终答案；标记最早失效层、信心和仍需的证据。
4. **做跨 Agent 同类盲评**：只选两侧均有权威来源的对应题型，分开报告“能力处理差距”和“知识覆盖差距”，不比较无关产品事实。
5. **复核原因与排序**：按影响的真实问题数、严重程度、可复现性和修复责任排序。输出每类一条可证伪的改进建议；此设计阶段不改生产行为。

最终交付包含：样本清单、逐题四轴判断、最早失效层与证据链接、版本身份矩阵、真实知识缺口清单、跨 Agent 同类对照、未定位项和优先处理顺序。分析报告不能只给一个综合分或“DAQ 比相机差”的主观结论；每个重要结论须能从原问题追到具体发布记录、工具结果与最终可见答案。

## 8. 范围边界

- 本文设计调查，不预先授权大规模重写、知识发布或生产部署。
- 相机知识不作为 DAQ 产品结论的来源；`tmp/` 原件、候选章节和用户附件不自动成为正式知识。
- 当前生产用户体验的判断须有实际生产 turn 或用户提供的答案。只有仓库代码和聚焦 Dev 回放时，结论限定在对应版本与题集。
- 生产只做现有证据的只读核对；任何新评测或模型消融均使用隔离 Dev，保留原始失败与版本身份。
