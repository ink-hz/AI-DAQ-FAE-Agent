# 数采规格检索链路复核（2026-10-12）

## 触发与证据

扩展真实原件 Dev 题批时，相邻两道规格题出现错误：HUB 单口供电输出虽有精确来源记录，却因“供电”只进入拓扑需求而弃答；EGO 1920 版可选 RGB 分辨率虽有精确来源记录，却因“有哪些”进入目录需求，模型按 `rgb_resolution` 查询而记录字段为 `rgb_resolution_options`。另一道 EGO 帧率题在取到正确记录后，仍因“在某分辨率下”额外生成分辨率需求、`frame_rate` 与 `rgb_max_fps` 不对齐，终态为 `invalid_answer_contract`。原始请求、工具调用、回答和 trace 保留在 Git 忽略的 `data/knowledge/curated/extended-dev-20261012/v1/`、`v3/`、`v5/`；成功复测另存 `v2/`、`v4/`，未覆盖失败。

## 共同原因与职责

`task_context` 负责从问题区分请求的规格与测量条件；现有宽泛词项把条件和数量问法误作另一能力。`DaqToolBox` 负责把模型字段名和实体参数对齐到已核对记录，但当前字段别名全局生效，无法表达同一个“RGB 分辨率”在不同实体下对应单值或可选值列表；模型传入 `umi-vision-module` 这类实体 ID 尾部时也无法命中。实体接地器在“EGO Pro + 1600×1200 测量条件”里曾把较短的 EGO 变体同时命中，造成需求实体为空。`EvidencePolicy` 按计划需求核对覆盖，正确地拒绝了未满足的终稿。问题发生在数采计划与检索边界，不能放宽证据门，也不能让候选章节或模型猜测代替结构化事实。

## 修正合同

1. 明确型号及字段的规格问法优先形成规格需求；“有哪些”仅在产品、型号、设备、套件等目录问法中形成目录需求。`在 1600×1200 分辨率下` 是条件，若同题另问帧率，不额外要求回答分辨率。
2. 规格字段同义词可映射到同一规范字段；只有已唯一接地的实体允许使用逐实体字段别名。别名仍由来源核对账本声明，不能把不同实体或泛称 EGO 的字段混用。`frame_rate` 与 `_fps` 的语义匹配只用于需求覆盖，不产生新事实。
   唯一实体可接受其稳定 ID 的尾部作为模型工具参数；不接受其他实体尾部。较短产品名仅在完全包含于较长名称且问题没有另一次独立提及时被较长名称遮蔽；同题提到两个产品保持歧义。
3. 用户明确说单个或每个端口时，`per_port=true` 可进入规格条件；泛称下游端口或显式矛盾条件不自动补齐。所有变体、分辨率和供电条件仍必须与记录精确匹配。
4. 验证按失败题先做合成红绿测试，再只重放受影响的真实 Dev 题；独立检查正文、结构化来源、覆盖、outcome 和 trace。若仍失败，继续按同一链路归因，不重试到通过。正式活动知识、认证角色、Platform 和相机服务不随本修订切换。

## 复审补充

独立代码复审发现两个证据误配风险：RGB 分辨率问题可能由 Mono 分辨率记录满足；问题同时提到“单口标称”和“四口同时输出”时，单口额定值可能被算作总输出。现将 RGB、Mono 的分辨率和帧率分别列成需求字段；四口同时/总输出明确要求 `per_port=false`，与单口 `per_port=true` 记录不能互相满足。合成回归覆盖错误工具调用仍不得满足需求。泛称 EGO 的变体提示也纳入逐实体别名，能列出两条已有来源核对的变体，仍标记非穷尽。修正后重新回放整批 10 题和四口边界题，结果见[Dev v2 来源核对与回放](2026-10-12-daq-dev-source-checked-v2.md)。

第二轮复审扩展了聚合端口问法：`四口`、`4口`、`多口` 与完整“多个下游端口”一样，在问同时/合计输出时要求聚合证据；真实 Dev 简写题安全弃答。
