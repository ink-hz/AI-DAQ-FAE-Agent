# 数采 FAE 开发任务书

> **执行定位**：这是跨仓总任务书。每个代码批次开工前，按本文接口和验收条件写该批的逐文件实施计划；逐任务完成测试、复审与提交。不得把整份任务书视为一次性上线授权。

**日期**：2026-10-08

**状态**：本任务书保留原始验收门；截至 2026-10-08，M0 与 A/P 的部分代码已在空知识本机 Dev 装配，但完整门禁均未通过，K 的真实资料发布和 V 的试点验收仍待完成。逐门实测状态见[接管门禁核查](../../reviews/2026-10-08-daq-takeover-gate-audit.md)，早期缺口见[能力对照审查](../../reviews/2026-10-08-bootstrap-capability-parity-audit.md)。

**目标**：交付面向内部 FAE/技术支持的独立数采 Agent，复用固定版本的现有 FAE 通用能力，独立发布知识与服务，并以真实 Dev 验收证明不会损害现有 FAE 的回答质量。

**设计基线**：[数采 FAE 完整设计](../../2026-10-08-数采FAE完整设计.md) v0.2；相邻 `AI-FAE-Agent` 仓库的需求、资料盘点、两方案决策和 `AI_FAE_Agent_工作流设计.md` 是约束。

**工程形态**：两个 Git 仓库、两个应用入口、各自的运行版本和知识发布；可以共用物理 Postgres 与模型网关，但数采使用单独数据库/用户、附件目录及 trace/反馈域。

**技术基线**：Python/FastAPI、现有 `LoopRuntime` 与 Anthropic 协议 Provider Adapter、Opus 5.5 adaptive/high 和 `submit_only_auto`；禁止给该模型发送 forced `tool_choice`。具体依赖版本以实施时锁定的上游源码和数采构建清单为准。

## 0. 全局约束与执行边界

- 首期仅内部 FAE/技术支持。终端客户自助、统一跨域入口、二进制自动分发和跨助手共享会话不在本任务书范围内。
- 能力编排按 `channel → context → guardrail → schema → Loop 取证 → coverage → synthesis → outcome → trace/eval` 实现；不恢复单桶路由或把旧 Planner 接回默认路径。
- 未裁决的型号映射、冲突参数和未授权资料不得成为确定答案或交付链接。`unknown`、`conflict`、`unsupported`、系统故障须分开。
- 所有模型回放与调参只在 Dev。生产不得运行评测；发布后只读检查健康、build identity、入口和日志，并分别观察 MetaBot/DingTalk 与后端。
- 任何 fallback 显示 `fallback_used`、`fallback_reason` 和 trace，非预期 fallback 在评测中失败。独立答案质量由 Codex 或具名 FAE 复审，回答模型不自评。
- 任务中提及的 `ai-daq-fae-agent` 是当前设计的数采 Agent ID。Platform 注册前若检测到 ID 冲突，先修订身份合同和本文，再实现；不能在两个仓库各用一个临时 ID。
- 每个共享内核改动均须在现有 FAE Dev 跑相关核心单轮、多轮、历史失败哨兵和泛化回归；按工作流层归因，零严重事实、权限或协议退化。

## 3. K：受治理数采知识

从原件处置、可读章节、事实一致性到独立 Dev 发布的细化任务、依赖与验收证据，见[数采 FAE 知识库专项任务书](2026-10-10-daq-knowledge-workstream-task-brief.md)。其中 K-1～K-4 仍是本总任务书的发布门；已有候选与合成演练不视为真实知识验收。

**执行方**：数采仓。

**交付物**：从已归档来源导入候选文本的离线流程；产品、规格主张、组合拓扑、步骤、软件关系、交付入口的稳定 ID 与适用条件；只读 `knowledge_release` 清单、差异审计和上一版回滚。

### K-2 首批产品与流程证据裁决

**执行方**：数采资料维护者；产品/研发负责人确认事实，资料所有者/渠道负责人确认可见与转发范围。

### K-3 软件证据、链接与内嵌模块事实

**执行方**：数采仓 + 相机事实维护者。

## 4. A：独立数采 Agent 应用

### A-1 API、身份与独立数据域

**执行方**：数采仓。

**交付物**：独立 `FastAPI` 装配与 `/chat`、`/attachments`、`/feedback`、`/health` 合同；单独数据库和数据库用户、附件目录、会话、反馈和 trace 存储；身份/资料权限过滤。`client_request_id` 防重复执行，SSE 心跳与完整/中断终态可区分。

**通过条件**：不调用现有 FAE 的相机专用 `src.api.server.create_app()` 或整个 `Orchestrator`；缺身份或 entitlement 时 fail closed，资料在检索/工具返回前过滤；断线重连不重复执行同一问题；终态含 `agent_id`、`runtime_release`、`knowledge_release`。旧 Agent 的会话、反馈和附件引用跨域拒绝。普通日志和 trace 不保存附件原文或含凭据链接。

### A-2 数采上下文、实体接地与证据需求账本

**执行方**：数采仓。

**交付物**：采集任务上下文保存设备/变体、主从、连接与供电、平台、Viewer/SDK/固件、存储/格式、已试步骤和错误证据；前置 schema 生成稳定需求 ID，工具结果更新 `satisfied / missing / conflict / unknown` 账本。

**通过条件**：短追问继承已确认条件，主题切换清除不适用条件；用户推测不能变成产品事实；空计划/空覆盖不算完整；trace 中的计划能力、实际能力和覆盖字段可由账本解释。不恢复固定单桶 Planner。

### A-3 领域取证工具

**执行方**：数采仓。

**交付物**：`resolve_entity`、`lookup_spec`、`inspect_topology`、`lookup_procedure`、`check_software_support`、`search_knowledge`、`sdk_evidence`、`official_links`、`session_state`，以及按授权启用的附件检索/精读/图片分析。数采 `ToolBox` 满足共享运行时的 `with_request_context`、`tool_schemas`、`dispatch`、`redact_tool_input`、`with_session` 合同。

**通过条件**：每个结果有状态、结构化来源、版本/适用条件和可诊断错误；组合拓扑不能从单件规格推导，`unknown` 不能被写成 `unsupported`；URL 工具提供本轮真实核验结果，工具名空壳不通过终稿门。附件只作为当前用户证据，不晋升官方知识。

### A-4 终稿、错误归因和可观测性

**执行方**：数采仓。

**交付物**：数采 `EvidencePolicy` 接入、`submit_answer` 终稿门、结构化 `sources`、outcome、fallback、trace 与评测记录。

**通过条件**：关键需求未满足不能 `resolved`；证据不足、需研发裁决、需人工 FAE 和运行失败各走正确 outcome。真正跨独立相机产品和数采套件的联合结论要说明证据边界并转人工协作，不把 EG-DB 的所有问题都转人工。Provider HTTP 400、`model_not_found` 被 503 包装、真实上游不可用、工具协议错、预算耗尽和附件失败可在 trace 中区分，不静默降级。来源路径只在结构化 `sources` 或来源区，不进入回答正文。

### A-5 版本、负载和独立回滚

**执行方**：数采仓 + 运行维护者。

**交付物**：Dev/试点配置隔离、镜像与知识双版本、可逆或兼容迁移、独立数采回滚、网关和 Postgres 共用资源监测。

**通过条件**：数采镜像或知识回滚不切换旧 FAE；共用资源排队、耗时、重试和错误可分别按 Agent 观察；资源争用超过试点批准上限时有配置回退或容量控制。保留发布前后 build identity 和回滚演练记录。

## 5. P：Platform 与渠道

### P-1 受控内部入口和授权联调

**执行方**：Platform 仓维护者 + 数采仓。

**交付物**：`ai-daq-fae-agent` 注册与内部卡片/WebUI/API 入口、身份绑定、受控内部 FAE 名单或资料 entitlement、反馈目标和附件授权合同。

**通过条件**：Platform 返回的 subject 真实绑定该 Agent；未授权角色看不到内容或链接；旧 FAE 的 Agent 身份不能访问新服务；入口与后端分别做健康观察。内部入口上线范围需在试点前明确，不能把“同属企业成员”当作资料权限。

### P-2 HTTP Task v1 与其他渠道

**执行方**：Platform 仓维护者 + 数采仓；按首期入口决策执行。

**交付物**：如首期启用 Platform Task/MetaBot，则注册新 audience/能力声明，按 `orbbec-http-task/v1` 联调任务、取消、幂等和终态；钉钉/MetaBot 入口另测。若首期仅 WebUI/API，则留下明确禁用配置与未接入状态，不能声称渠道已可用。

**通过条件**：跨 Agent task token、重复任务、取消后继续输出和渠道断线均有可追溯结果；入口故障与后端故障可分别定位。未完成联调的渠道不得暴露给试点用户。

## 6. V：验收、试点发布与证据包

### V-1 冻结评测集并做静态/合成门

**执行方**：数采仓 + 独立复审人。

**交付物**：预注册的核心单轮、多轮、上一轮失败哨兵、catalog/spec/selection/SDK/troubleshooting/boundary 泛化集；实体、冲突、权限、链接、账本、终稿和错误归因的确定性测试。

**通过条件**：覆盖 EGO 1600/1920、EGO Pro 100/120 mm、Wi-Fi 5/6、EG-DB 模块/整机、EGO + 双 WristCam + HUB、Viewer/固件版本、未授权链接与检索前权限、Provider 400/503、多轮和附件；样本、预期结果与评分规则在真实回放前冻结。测试要求映射见第 7 节。

### V-2 真实 Dev 回放和独立质量复审

**执行方**：数采仓 + Codex/具名 FAE；现有 FAE 维护者复核共享改动。

**交付物**：逐题问题、完整答案、计划/实际能力、证据覆盖、来源、fallback、outcome、trace_id、耗时、模型/网关版本、复审人、质量结论、失败原因与工作流层级；旧 FAE 受影响路径的 Dev 回归记录。

**通过条件**：零严重事实/型号混答、零未经授权资料/链接交付、零无据 `resolved`、零运行错误误报为业务缺证、旧 FAE 零严重退化。非空回答、有 sources 或自动结构分数都不能代替独立语义复审。所有失败回到对应层修根因并重新跑相关泛化集，保留原始失败记录。

### V-3 性能门、回滚演练与试点决策

**执行方**：数采仓 + 运行维护者 + 内部试点负责人。

**交付物**：从现有 FAE 基线与数采 Dev 回放冻结 p95/p99、Provider/工具调用、排队、重试及共用资源压力上限；身份/资料裁决清单；镜像和知识独立回滚演练；只读发布后检查与监测方案。

**通过条件**：批准的阈值有实际测量依据；可见资料均有授权和裁决人；新旧服务的版本、入口、数据库、知识和回滚目标可分别识别。未满足任一硬门时保持 Dev/受控内测状态，不把设计完成或静态测试通过写成已上线。
