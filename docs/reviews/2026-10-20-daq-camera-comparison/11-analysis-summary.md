# DAQ / 相机 FAE 完整证据对照结论

**调查范围**：2026-10-20 两仓源码与发布快照、相机带版本 Dev 回归、DAQ 六条历史隔离 Dev 失败、16,942 条本地 trace 的身份/时间元数据、知识原件审计、逐题独立复审、正式主知识下的无模型工具和终稿合同探针。A0–A10 的可访问证据均已核查；两服务**当前生产**构建/知识/模型身份和用户本次线上短答原题/trace 因内部入口不可达且用户案例缺失，保持精确观测阻断。本页不宣称已经定位该次线上请求的根因。分析记录从[索引](index.md)进入，八项发现及反证见 [10-findings.md](10-findings.md)。

## 已经能回答的问题

1. **移植时通用运行时代码是否不同？** 两仓 `HEAD:src` tree 相同；不能把“共享 Loop 被复制坏了”作为当前仓库版本的解释。实际装配不同：相机当前 Loop 未注入可选领域证据 policy，DAQ 注入严格的需求账本 policy；DAQ 另加领域 schema、知识角色及发布链。质量损耗主要需沿这些差异和实际部署身份查。
2. **“回答短、答不出”是否全是知识不足？** 不是。旧 `CASE-001` 17 字来自 schema 错误；旧 `CASE-003/004` 已取得流程或四条 FOV 证据却没有正确认领/交付；旧 `CASE-005` 工具知道 SDK 版本而终稿说不知道。最终本机代码与正式主知识的无模型探针进一步证实：已知流程或四值已检出时，漏交付的假设 `safe_abstained` 仍获 `allow`（`FIND-008`）。另一方面，三设备同步、整机总供电、精确软件组合和官方链接确实无足够已审发布证据，应保留未知。
3. **上下文是否整个丢了？** `CASE-005` 的同轮工具参数仍含 2.9.0，排除“整轮完全没带上文”。认证入口有带来源轮次的 checkpoint；旧案问题是结构化目标和终稿对已知字段的兑现不稳定。切题/纠正的当前生产效果尚未逐请求核对。
4. **模型/网关或页面是否导致这些旧案？** 四条保存完整事件的旧案有 Provider 模型回显、无重试/协议错误、预算未耗尽，SSE 与历史答案一致；这些旧案的首因不在网关截断或 SSE/历史丢字。当前线上 UI/模型身份仍未知。
5. **为何已有修复仍需警惕？** 最终代码的部分聚焦 Dev 复审通过，10-20 正式主知识和 SDK 五题复审也有证据；但最终代码+正式知识身份下核心 55 题未整套跑，13 组多轮只完成 9 组。旧知识身份的核心/多轮复审随代码版本出现过先通过、后回退，不能把旧身份或局部通过折算为整套发布通过。
6. **Dev 与认证入口真的等价吗？** 10-20 源码不是：Dev 给 DAQ 证据策略传有效问句，认证聊天与 Task 没传。无模型对照中，一条无来源的 USB 连接说法在前者被要求改写、后者被放行（`FIND-007`）。这是已证装配差异，尚未证明它引发本次线上短答。
7. **知识库的损耗到底在哪里？** 当前主知识发布把 276 个原件纳入库存，但 27 条可答记录（0 章节）的 29 处引用只落在 9 个唯一原件上；历史全量审计另有 42 件仅候选、225 件仅归档。以本批 12 个原子需求为分母，7 个有角色可见已审证据、5 个不足。9/276 是引用范围，绝非答案正确率；已发布但没交付与根本没有受审证据必须分开处理。
8. **现在的线上请求能否闭环？** 本地 16,942 条 trace 截至发布前 00:49 UTC，最终运行时/主知识 ID 均为零；本机内网健康接口不通，公网健康接口 404。故本次具体用户请求仍缺原问、答案、角色、trace 和当前生产身份；这是明确的证据缺口，不是又一轮泛泛“待分析”。
