# DAQ non-root deployment preparation

This is a deployment candidate, not authorization or evidence to cut over. Use the exact existing image ID `sha256:5ed10ead83ee10ad5ef668fad8ee6aa7d28e37bb8d217fd22daa84d6d5db5bf7`; do not build or pull. The independent native gates V01–V11 and the production observation V12 in `2026-10-29-daq-nonroot-design.md` remain mandatory. The controller owns container, image, UID collision, mount, trace reader/rotation, quiescence, Docker/Compose compatibility, rollback and actual release checks. Never run this tooling against a live writable source and describe the result as a cold capture.

`security_assets.py` requires effective root. Output parents and every ancestor must be root-owned and not group/other writable; targets must not exist. Supply absolute paths with no symbolic-link components. It never changes a source file or its ownership. The output batch must be outside every source tree; source paths and every source path component are opened without following symbolic links. It creates a private target (0700) and, on successful asset staging, exposes its root as root:21081 0750. Secret and content key copies are 21081:21081 0600; entitlement and approval key copies are root:21081 0640; RO knowledge files are root:21081 0640 with directories 0750. New attachment and trace data are 21081:21081, directories 0700 and files 0600. Docker must mount the RO leaves read-only. Inspect actual native owner and permission behavior separately; host-side mocked tests do not prove it.

Every command reads a root:root 0600 JSON spec. The spec carries paths, SHA-256/size identities, and metadata, never key contents. Collect the expected inventory independently and privately; it is a required controller input, not a hash of an unverified copy. Inventories must cover every regular file under each selected knowledge root and the complete attachment tree; list exactly the four referenced secrets and the single trace. The tool does not copy other secrets or historical knowledge roots. Inventory identity must bind the published version and be rechecked for drift; a missing or extra file aborts. Files over 64 MiB, a stage total over 256 MiB, more than 4,096 target entries (including batch root, manifest and directories), more than 128 directory levels, links (including hard links) and special files are refused. Sources are opened component by component with no-follow descriptors, fstat checked, copied with exclusive targets, checked by hash and re-read after copying, and the new tree is checked again. Fsync is used for files and directories. Before copying, the helper checks source entry count and byte sizes, computes a conservative upper bound for the generated manifest against its 16 MiB read limit, and requires the destination filesystem to have those bytes plus a 512 MiB reserve. It records this private preflight; the controller must also remeasure shared-host disk headroom and account for other concurrent consumers. After final ownership and mode changes it records destination file and directory dev/inode/metadata and all empty directories; pre-start verify reopens descriptors and checks identity, membership, permissions and hashes together. The tool reports only stage/matched on stdout or stderr; detailed `manifest.json` is root-private and contains sensitive paths, hashes, identities and attachment names. Never put it in a general report or log.

The abbreviated inventories above are examples, not complete inventories. Empty attachment trees use `{}`. Keys in each `config_files` object must appear in the same order as the comma-separated `com.docker.compose.project.config_files` label. `labels_file` is a controller-captured JSON object containing at least the actual container's `com.docker.compose.project`, `com.docker.compose.service`, `com.docker.compose.project.config_files`, and `com.docker.compose.project.working_dir` labels. The caller must supply the captured project name and matching absolute `project_directory`; the Compose process is explicitly run with that directory. The example project name is illustrative, not a default. The labels file is root:root 0600. The tool validates the evidence bytes and those files against the caller's expected hashes, but cannot establish which running container supplied the evidence. The controller must independently validate that provenance and identity. `old_data_dir` must be the actual old `/app/data` bind source. The input main, SDK, attachments and trace paths must be the corresponding exact leaves inside it, and `old_secrets_dir` must match both the original secret source and the original Compose mount. The helper requires a single source service, the existing two data/secrets binds, loopback port, named external networks and restart/health contract. Unsupported source security features, extra mounts or services fail closed rather than being silently dropped.

The controller supplies the exact trusted Compose front-end executable and its SHA-256. Every path component and the executable must be root-owned without group/other write access; provide a real path, not a symlink. Production must use the independently verified Compose 2.40.3 binary; local tests explicitly use the installed 5.6.0 binary with a substituted local ownership check, which does not establish production equivalence. `interpolation_file` is a controller-constructed root:root 0600 Compose env file containing the complete approved interpolation context; its bytes must match the explicit hash. The process environment is empty, the context is passed explicitly, and any Compose warning, unset interpolation, parser error, input drift, timeout or excessive output stops the operation. No shell fallback or ambient Compose environment is used.

Before overlay and again on each parsed effective runtime and rollback model, one execution-boundary policy classifies every service field. It rejects unreviewed fields and nonempty `volumes_from`, service secrets/configs, Docker API socket, devices/device rules/GPU, supplementary groups, added capabilities, privileged mode, lifecycle hooks, host/shared PID/IPC/UTS/user namespaces, `network_mode`, and unexpected tmpfs. `deploy` is limited to ordinary CPU/memory/PID resource controls (an empty Compose-generated placement object is accepted); device reservations and other deploy capabilities fail closed. The only accepted security option is no-new-privileges, source and rollback must be the registered root baseline, and runtime must have the exact non-root policy. The old source must have its two registered binds; the runtime and rollback each must have exactly five reviewed leaf binds. Endpoint aliases, extra network addressing and extra published ports are rejected. Commands, entrypoints, environment, ordinary resources and logging remain supported and are checked through effective-model comparison. An unsupported or future service field fails closed with a sanitized reason; arrange a separate review before extending the allowed contract.

The helper reads ordered original inputs using the pinned Compose front end in both raw no-interpolation mode and complete effective mode. It does not rely on `--no-env-resolution` to retain references: Compose 2.40.3 can still resolve and discard `env_file` in that mode. The raw models preserve the `env_file` reference and explicit environment separately; an isolated reference-only echo model and a second raw path model, both parsed by the same front end and controlled context, resolve the reference without importing env-file contents. The reference origin is obtained from Compose’s own path-resolved raw model, not guessed from a filename. Ambiguous origins fail closed. The resolved reference must equal the explicitly supplied original env file, and the original explicit environment expressions are retained for the subsequent complete re-parse. It checks the original env-file hash and compares the actual effective production authentication, exact selected paths and approval public-key pin, not physical lines. It overlays only the documented image/security/leaf-mount changes on the complete normalized model; all other supported fields such as logging, resources, command, entrypoint and explicit environment remain intact. Runtime and rollback are separately re-parsed and privately compared against the effective source, including complete environment equality except the two intentional runtime overrides. Resolved service `env_file` values are never printed or copied into the generated model. Pre-existing explicit `environment` entries, including any literal sensitive values, remain in the private model as declared and are resolved on re-parse with the controlled context; stdout, stderr and argv never contain their values. Each generated model is capped at 16 MiB. The controller must compare privately on the actual production Compose 2.40.3 front end and independently prove that the supplied interpolation context is the context of the current deployed container; a hash alone cannot establish that provenance.

1. During live service, stage only the RO material with `python3 deploy/security_assets.py stage-ro --spec /absolute/private-spec.json --target /absolute/new-ro-batch`. It does not copy attachments or trace. Recheck published active identity and source inventory before proceeding; render/verify also re-read original main, SDK, secrets, attachments and trace against the staged source identities. The controller still establishes that these are the current published roots and that no writers can race cutover.
2. The controller stops only DAQ and establishes that uploads, workers and leases are quiescent. Capture the controller's evidence in a separate root:root 0600 JSON file: `{"container_id":"<64 lowercase hex>","image_id":"sha256:5ed10ead83ee10ad5ef668fad8ee6aa7d28e37bb8d217fd22daa84d6d5db5bf7","stopped_at":"2026-10-29T00:00:00Z","quiescence_evidence":"sha256:<controller-evidence-sha256>"}`. The tool records this as `controller_asserted_not_verified`; it cannot verify Docker state or writer quiescence. Independently capture the current complete attachment/trace inventory after stopping. Run `python3 deploy/security_assets.py capture-rw --spec /absolute/private-spec.json --target /absolute/new-rw-batch --stopped-evidence /absolute/private-evidence.json` while still quiescent.
3. Run `python3 deploy/security_assets.py render --spec /absolute/private-spec.json --target /absolute/new-config-batch`, then `python3 deploy/security_assets.py verify --spec /absolute/private-spec.json --target /absolute/new-config-batch` immediately before a controller-approved start. Rendered `runtime.json` and `rollback.json` are root-private Compose JSON files. Both use the exact old image, `pull_policy: never`, same loopback port/networks/address/restart/health, RO knowledge and leaf RW paths. The rollback omits the non-root security overrides, uses the original secrets and keeps **current new** attachments/trace and the unchanged external PG. No broad `/app/data` mount is generated. Verify checks identities, hashes, permissions and the effective Compose model using the explicitly pinned front end. It does not inspect the running container or establish evidence provenance. Validate those separately on the isolated native host without exposing expanded env.
4. After the service has written data, the captured RW manifest is deliberately stale: do not present `verify` against that old inventory as a post-write or rollback acceptance. Use the previously verified rollback config after stopping writers; do not overwrite new data from the old snapshot or restore PG. A later re-forward after root recovery needs a fresh stopped-source copy into another exclusive batch because root may have created root-owned files. No online recursive chown.

Any failure after a new target is created leaves a private `failure.json` with a sanitized reason/category and partial target; it is not published as a successful batch. Failures before an exclusive target can be safely created (including bad inputs, unsafe parents or collisions) cannot leave a receipt there. Preserve the controller's sanitized command result and inspect private evidence; never overwrite or reuse a failed target. `verify` is read-only and leaves no receipt. An existing valid batch is never overwritten.
